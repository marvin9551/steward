# 设计决策

[English](../decisions.md) | 简体中文

这里简短记录塑造本项目的选择。每条都写明备选方案，这样将来改动时是在和"理由"辩论，而不是和代码辩论。

## 1. 用 asyncio，不用线程

**决策：** 整个运行时是 `async`；阻塞型工具通过 `asyncio.to_thread` 放到工作线程。

**理由：** 流式输出、单次工具超时、取消、多渠道路由，本质都是 I/O 等待。`asyncio.wait_for` 一行就能表达超时；线程池则需要队列、哨兵值和一种"放弃任务"的方式。

**代价：** 阻塞操作需要留意（必须 `to_thread`），CPU 密集型工具仍会占住一个 worker。

## 2. 手写 OpenAI SSE，不用 SDK

**决策：** `httpx` + 约 90 行 SSE 与工具调用拼装。

**理由：** 这是一个学习项目，而"线上格式"正是最值得学的东西。按 `index` 拼装 `tool_calls`（参数被拆在多个 `data:` 分片里）是每个 Agent 里最不直观的部分，SDK 会把它藏起来。

**代价：** keep-alive、`[DONE]`、坏 JSON、各家实现差异都要自己处理。生产环境里官方 SDK 是更稳的默认选择；`Provider` 协议意味着换 SDK 不需要动主循环。

## 3. SQLite、只追加、保存模型消息

**决策：** 一张表、JSON payload、不更新、不用 ORM。

**理由：** 对话就是一个有序日志。只追加带来确定性回放、简单备份，以及未来做分支的路径。保存"模型看到的消息"（而非渲染后的文本）让 `history` 成为真正的调试工具。

**否决的备选：** JSONL 文件（查询/过滤不便）、Postgres（单人使用没必要）、ORM（这个体量只增加一层）。

## 4. 按完整 turn 裁剪

**决策：** `context.fit()` 保留能放下的最新若干个 turn，绝不从 turn 中间切。

**理由：** 带 `tool_calls` 的 assistant 消息和它的 `tool` 结果是同一个单元。从中间切开会构造出所有 provider 都会拒绝的请求。相比直接丢弃 turn，优先压缩工具输出——一段 40KB 的文件读取通常没有"导致这次读取的对话"有价值。

**暂缓：** 对被丢弃 turn 做摘要。将来实现时，摘要作为 system 消息插入，磁盘上的日志保持不变。

## 5. 不用 Agent 框架

**决策：** 不引入 LangChain / LlamaIndex 等。

**理由：** 主循环很小，而框架的抽象（chains、runnables、callbacks）会遮蔽这个项目要教的四个步骤。框架提供的集成点——模型适配、工具 schema、重试——这里每个都不到 100 行。

**代价：** 重试、schema 校验、provider 差异都要自己维护。这正是目的，但也是真实的维护成本。

## 6. 工具限定在一个工作目录

**决策：** 所有文件路径都会解析并校验是否位于工作目录内，**所有权限模式都一样**。

**理由：** 用户真正害怕的故障是"助理删错了文件"。单一目录边界容易推理，也容易在系统提示词里讲清楚。

**局限：** shell 命令仍然可以访问工作目录之外。这就是为什么 `workspace-write` 模式下每次变更都需要审批，也是 README 明确说"这不是沙箱"的原因。

## 7. 先做审批，暂不做操作系统沙箱

**决策：** 最高风险的操作每次调用前询问，除非 `--yes` / `auto_approve`。`workspace-write` 模式里是 shell；后来加的 `ask-before-write` 模式用同一套机制把询问扩展到文件写入和编辑——"助理改错文件"和"助理执行了命令"一样值得人过目。

**理由：** 笔记本上的个人助理是在用户自己的账号下执行命令；真正的边界需要 bubblewrap（Linux）或 Seatbelt（macOS）以及挂载策略。那是独立阶段；把"子进程环境变量白名单"说成沙箱，比承认它不是更糟。

**下一步：** 类似 `execution/sandbox.py` 的后端，按平台选择，并在启动横幅里明确显示"已沙箱 / 未沙箱"。

## 8. 用事件，不直接 print

**决策：** runner 发出类型化 dataclass；只有 `cli.py` 负责打印。

**理由：** 第二个前端（Web UI 或聊天渠道）的成本就变成一个渲染器，而不是一次重构。测试也能断言事件，而不是抓 stdout。

## 9. 子进程不继承密钥

**决策：** `run_shell` 只传一小份环境变量白名单。

**理由：** 父进程环境里有 API Key。像 `env` 这样的命令或第三方脚本会把它们打印进对话，随后被存进 SQLite 并发给模型。CLI 真正需要的变量可以显式加入白名单。

## 10. 先做 CLI，再做 Web

**决策：** v0 的唯一界面是 REPL。

**理由：** REPL 用约 100 行就能验证主循环、流式输出和审批流程。在事件模型稳定之前做 Web UI 只会返工。Roadmap 在循环不再变动之后再加 SSE 端点和单页界面。

**现在：** 循环确实稳定了，P3 加上了页面——runner 一行没改，只多了两个 `on_event` 的消费者。见决策 11、12。

## 11. 用标准库 HTTP 服务，不用 Python Web 框架（已被 13 取代）

**决策：** `http.server.ThreadingHTTPServer` 加手写路由、JSON 与 SSE。页面是 `web/` 里的 React 18 + Vite + Tailwind + shadcn/ui，构建进 `steward/web/static/`。

**理由：** 八个接口不需要路由框架、依赖注入层或 ASGI 服务器，跳过 FastAPI 让安装依赖保持在一个包。前端反过来是有意的：shadcn/ui 是把源码复制进来的组件，可读、可改，一套真正的组件库值得一次构建步骤。

**代价：** 请求解析、错误响应、静态文件服务都要自己写（约 280 行），改页面需要 Node。构建产物已提交，所以运行它永远不需要。

**已被取代：** 线程带来的代价被证明是笔错误的交易，见决策 13。前端那一半的决定仍然成立。

## 12. 同时只跑一轮，用游标而不是队列

**决策：** `WebService` 只保留一个 turn 槽位，第二个 `POST /api/turn` 返回 409。`GET /api/stream` 是对一个有界内存事件日志的游标，而不是持久队列。

**理由：** 一个人问一个助理一个问题，这才是真实用法；两轮同时写进同一个会话会得到没人愿意读的历史。有界队列加游标天然带来回放与续传，而持久日志仍然在原来的 SQLite 里。

**代价：** 落后超过缓冲区的客户端会收到 `resync`（从 SQLite 重新加载），而不是逐个事件补齐。因此它可能错过当前步骤正在流式输出的增量，但已提交的历史永远不会丢。

## 13. Web 层用 FastAPI，作为可选依赖

**决策：** Web API 用 FastAPI + uvicorn（`steward/web/api.py`、`server.py`），通过 `pip install -e ".[web]"` 安装。Agent 主循环仍然只有一个运行时依赖。

**理由：** 手写的 `http.server` 版本能跑，但它用错了货币来换「小」——每个 SSE 连接一个线程、每一轮一个自带事件循环的线程、审批要靠 `threading.Event` 搭桥。换成 ASGI 之后，一轮就是一个 `asyncio.Task`，一次审批就是一个 future，SSE 就是一个异步生成器：正是决策 1 早就为运行时选定的原语，不再需要第二套并发模型。请求校验、统一的错误结构、`/docs` 都是顺带得到的。

**代价：** 想要界面的人多装两个包，还要熟悉一套框架约定。做成可选依赖，CLI 安装就仍然只有一个依赖；没装时 Web 测试会自动跳过。

**没有变的部分：** HTTP 契约、页面、`Runner`，以及「行为都在 `service.py`、路由保持很薄」这条规矩。

## 14. 页面改的是覆盖文件，永远不重写你的 config.toml

**决策：** 网页的设置对话框把修改持久化到 `~/.steward/settings.toml`，由 `config.load()` 叠加在 `config.toml` 之上生效。`STEWARD_*` 环境变量仍然优先，环境钉住的字段在页面上直接拒绝修改。

**理由：** `config.toml` 是你手工编辑、带注释的文件，从表单里悄悄重写它是恶劣行为。单独的覆盖文件让页面拥有自己的一块地盘，「撤销页面的所有修改」变成删一个文件，也让既有的优先级叙事保持为真：默认值 < config.toml < 覆盖文件 < 环境变量。

**代价：** 多了一个取值来源，所以对话框会写明保存落在哪里，并锁住环境已设置的字段。API Key 在 HTTP 上只写不读——GET 只返回布尔值——因此存进去的 key 永远无法从页面读回来。

## 15. ask-before-write：所有变更都先询问的一档

**决策：** 新增第四档权限 `ask-before-write`：读操作放行，每次写、编辑和 shell 调用都先询问。`workspace-write` 含义不变——工作目录内文件自由写，shell 询问。（本条取代此前短暂落库的「让 workspace-write 自己也写前询问」方案：悄悄改变**默认**模式的含义，对既有会话是一次无声的行为变更。）

**理由：** 原有三档对应三种信任级别，但人们真正想要的那一档缺失了——"随便看，但每次改动发生前给我过目"。只对 shell 询问并不够：覆盖一个用户在乎的文件和执行一条命令同样值得看一眼，而同一套审批机制本来两者都能承载。

**代价：** 这档话多——长重构会产生很多张卡片。逃生口不变（`--yes` / `auto_approve`，以及审批卡里按工具的「始终允许」，本次进程内有效），系统提示也会叮嘱模型把改动做小、不把无关编辑打包进一次调用，让审批保持可读。
